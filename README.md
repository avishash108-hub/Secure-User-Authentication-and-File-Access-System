# Secure User Authentication and File Access System

## Overview

This project contains two implementations of a secure user authentication and file-access system:

1. **Custom implementation:** Python Flask + PostgreSQL
2. **Appwrite implementation:** Appwrite Authentication, Database, and Storage

Both implementations support authenticated users, user-specific profile information, and access to files belonging to the authenticated user.

The custom implementation was built with security and separation of responsibilities in mind: PostgreSQL stores application data, Flask handles the API and authorization logic, and the filesystem stores the actual downloadable files.

# 1. Custom Flask + PostgreSQL Implementation

## Authentication Design

### Why JWT instead of server-side sessions?

I chose JWT-based authentication for the custom REST API because it fits the API-oriented design of the application and allows authenticated requests to carry the user's identity without requiring the application to maintain a traditional server-side login session for every access-token request.

I specifically used a **short-lived access token + longer-lived refresh token** design.

The access token contains claims such as:

```json
{
  "u_id": "usr_001",
  "type": "access",
  "exp": "..."
}
```

The refresh token contains:

```json
{
  "u_id": "usr_001",
  "type": "refresh",
  "jti": "...",
  "exp": "..."
}
```

JWTs are signed using **HS256**, which uses HMAC-SHA256 internally. The signing secret allows the server to verify that the token was generated by the trusted backend and has not been modified.

I chose this approach because it gave me a clear separation between authentication at login time and authorization on subsequent API requests:

```text
Login
  ↓
Password verification
  ↓
Access token + Refresh token
  ↓
Protected API request
  ↓
Verify JWT
  ↓
Extract trusted user ID
  ↓
Authorize database/file access
```

The access token is intentionally short-lived, while the refresh token provides a longer-lived mechanism for obtaining a new access token.

---

## Password Hashing and Why Argon2

Passwords are never stored as plaintext.

I chose **Argon2** for password hashing because it is designed to be memory-hard as well as computationally expensive. This makes large-scale password guessing and brute-force attacks more expensive than with a simple fast hash.

Argon2 also handles salts as part of the password-hashing process, meaning the same password does not produce the same stored hash for every user.

During login, the submitted password is verified against the stored Argon2 hash rather than being hashed manually and compared as plaintext strings.

## JWT Middleware

Protected endpoints use a reusable Flask decorator.

The decorator:

1. Reads the `Authorization` header.
2. Verifies the `Bearer` scheme.
3. Extracts the JWT.
4. Verifies the token signature and expiration.
5. Verifies that the token is an **access token**.
6. Extracts `u_id` from the verified payload.
7. Passes that trusted `u_id` to the protected endpoint.

This means protected routes do not trust a user ID supplied by the client.

---

## User Data Isolation

User isolation is enforced by taking the user's identity **only from the verified JWT**.

For example, the files endpoint uses the authenticated `u_id`:

```sql
SELECT file_id, file_name, mime_type, size_bytes, uploadedAt
FROM files
WHERE u_id = %s;
```

For direct file access, both the requested file ID and authenticated user ID are checked:

```sql
SELECT file_name, mime_type, file_path
FROM files
WHERE file_id = %s AND u_id = %s;
```

This prevents a user from simply changing a user ID in a request and accessing another user's data.

The trust boundary is therefore:

```text
Client request
     ↓
Signed JWT
     ↓
Verified u_id
     ↓
Database authorization condition
     ↓
User-owned data only
```

The client supplies the requested resource ID, but **not the identity used to authorize ownership**.

## Logout Implementation

JWT access tokens are stateless, so simply deleting a token on the client would not provide server-side invalidation.

To implement logout, refresh tokens contain a unique `jti` value.

A server-side table stores the refresh-token session:

```text
jti
u_id
expires_at
revoked
```

When the user logs out:

```text
Refresh token
    ↓
Verify token
    ↓
Extract jti
    ↓
Mark refresh session as revoked
```

The refresh endpoint checks the corresponding session before issuing a new access token.

Therefore:

```text
Before logout:
refresh token → valid → new access token

After logout:
refresh token → revoked → 401
```

The current implementation intentionally keeps access tokens short-lived. A previously issued access token may remain valid until its normal expiration, while the revoked refresh token can no longer be used to obtain new access tokens.

## File Access and Download

The database stores metadata about files, including the file path, while the actual file contents are stored in the local `storage/` directory.

The download flow is:

```text
GET /files/<file_id>
        ↓
Verify access JWT
        ↓
Extract authenticated u_id
        ↓
Check file_id + u_id in PostgreSQL
        ↓
Retrieve server-controlled file path
        ↓
Build filesystem path
        ↓
send_file(...)
        ↓
Actual file returned to client
```

`os.path.join()` is used to construct the filesystem path from the application root and the relative path stored in the database.

The client does not supply an arbitrary filesystem path.

---

## Rate Limiting

Basic rate limiting is applied to the login endpoint to reduce repeated authentication attempts and brute-force abuse.

The current implementation uses Flask-Limiter and limits requests from the same client according to the configured rule.

# 2. Appwrite Implementation

The Appwrite implementation uses Appwrite's managed services instead of recreating the authentication, session, database, and file-storage infrastructure manually.

The Appwrite project contains:

* Email/password authentication
* A `users` table
* A `files` table
* A Storage bucket for user files
* Per-user file permissions
* Three seeded test users
* User-specific files

The Appwrite database tables use the same application-level columns as the PostgreSQL implementation where appropriate so that both implementations follow the same overall data model.

### Users table

```text
u_id
email
password_hash
full_name
display_name
bio
created_at
role
```

### Files table

```text
file_id
u_id
file_name
mime_type
size_bytes
uploadedAt
file_path
```

The `password_hash` field is part of the mirrored application data model, but **Appwrite Authentication manages passwords itself**. The Appwrite implementation does not use the PostgreSQL Argon2 hashes for authentication.

---

## What Appwrite Handles Automatically

Appwrite provides managed functionality that had to be implemented manually in the Flask version, including:

* User authentication
* Password storage and authentication handling
* Session management
* Authentication-related APIs
* File storage
* File delivery
* Permission enforcement for protected resources
* Database service infrastructure

This significantly reduces the amount of security-sensitive infrastructure that needs to be implemented manually.

---

## What I Configured Myself in Appwrite

I configured:

* Email/password authentication
* The three seeded users
* Database and tables
* User and file data model
* Storage bucket
* File-level permissions
* User-specific ownership/access rules
* Seeded file associations
* Project/web platform configuration

The most important isolation configuration is that files are given permissions corresponding to their intended user, so one authenticated user cannot read another user's files.

# 3. Setup Instructions

## Flask + PostgreSQL

### Install dependencies

```bash
pip install -r requirements.txt
```

### Environment configuration

Copy:

```text
.env.example
```

to:

```text
.env
```

and provide the local PostgreSQL credentials and JWT secret.

Example variables:

```text
DB_HOST=localhost
DB_PORT=5432
DB_NAME=your_database
DB_USER=postgres
DB_PASSWORD=your_password
JWT_SECRET_KEY=your_secret
```


Run the provided `seed.sql` against the PostgreSQL database.

The `storage/` directory must remain in the project so that the seeded file paths resolve correctly.

### Run the Flask server

```bash
python app.py
```

The API will be available at the configured local Flask address.

# 6. Future Improvements

Given more time, I would improve the project in several directions.

### Security and robustness

* Add refresh-token rotation and reuse detection.
* Strengthen request validation for malformed and unexpected inputs.
* Expand negative testing across all endpoints.
* Improve CORS configuration for deployment instead of relying on broad development settings.
* Add stronger abuse controls and infrastructure-level protection against large-scale denial-of-service(DoS) traffic.
* Add audit logging and more detailed security monitoring.

# Conclusion

The custom implementation focuses on understanding and explicitly implementing the security mechanisms behind authentication, authorization, password hashing, token management, user isolation, rate limiting, and file access.

The Appwrite implementation demonstrates how managed backend infrastructure can provide many of these capabilities automatically while still requiring deliberate configuration of data models, storage, and permissions.

Building both versions provided a direct comparison between implementing security-sensitive backend functionality manually and configuring a managed backend platform.
